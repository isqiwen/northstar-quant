# 审计修复与上线门槛

## 当前可信边界

本仓库已经完成以下失败关闭修复：

- `weight_return` 回测真实应用初始资金、佣金、最低佣金、滑点和执行延迟；
- 持仓快照用独立批次头表达空仓，并按 broker、account、profile 查询；
- 数据制品包含内容哈希和 profile 指纹，加载时重新校验 schema 与 universe；
- production 画像必须显式启用资金、交易状态和价格限制等动态风控；
- 批次中一笔订单失败会停止后续路由，并继续记录运行健康；
- 全状态对账在一个数据库事务中提交，失败时整体回滚；
- 日报、周报、月报使用各自真实期间，月报仅在月末交易日发送；
- 实际合约逐日状态机检查含成本保证金，并按换月价差平移保护价。

## Paper 的含义

仓库内 `PaperBrokerAdapter` 用于验证订单持久化、成交生命周期、对账、归因与报告。它
采用现货式现金记账，不实现期货保证金、合约乘数、平今/平昨和结算规则。测试中的
paper 闭环只能证明基础设施可以协作，不能证明期货策略具备可交易性。

当前没有内置实际期货 execution planner，也没有 simulated 或 production 画像。连续
合约画像仍会在生成订单计划前被硬阻断。

## 创建 simulated 画像前

必须先准备：

1. 实际交割合约历史行情和不可变 manifest；
2. 经核验的合约乘数、tick、动态保证金、手续费与交易时段快照；
3. 明确的目标风险到手数换算模型；
4. 开仓、平仓、平今、平昨和反手语义；
5. 使用期货记账规则的模拟 broker；
6. 数据、信号、计划、成交、对账、报告的端到端回归测试。

## 创建 production 画像前

除 simulated 条件外，还必须完成：

1. CTP 认证、结算确认、报单、撤单和查询适配器；
2. 断网、超时、迟到回报、重复成交、部分成交和进程重启演练；
3. 真实交易数据提供器白名单与数据内容核验；
4. 交易所日历、夜盘和节假日前后会话验证；
5. kill switch、人工审批、账户隔离和恢复手册演练；
6. PostgreSQL 环境中的迁移、并发租约和故障注入测试。

在以上条件全部满足前，`NORTHSTAR_BROKER` 应保持 `paper`，
`NORTHSTAR_LIVE_TRADING_ENABLED` 应保持 `false`。
