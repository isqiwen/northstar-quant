# 架构审核与演进路线

审核日期：2026-07-23

## 审核结论

Northstar Quant 已经具备清晰的模块化单体雏形，研究、回测、paper 和 live 共用 canonical strategy pipeline。包级循环依赖已经清零，并有自动边界测试防止回归。

项目已经落地订单提交幂等、账户级跨进程租约、正式 instrument registry 和
completed/cancel 终态恢复，但仍不满足真实资金解锁条件。当前阻断点转为：
registry 尚未录入经账户持有人核验的 conId、production 数据仍是 demo，以及
尚未完成 PostgreSQL 并发、进程强杀、断网恢复和 paper soak 演练。

## 本轮完成的优化

### 依赖与职责

- 数量规则和订单状态下沉到 `common`。
- `risk` 通过 Protocol 接收订单风险输入，不再反向依赖 `execution`。
- IBKR 基础设施移入 `execution`，对账移入 `live`。
- 运行健康汇总移入 `monitoring`，解除 `live ↔ reporting`。
- 增加核心依赖 allowlist 和全包无环测试。

### 配置与策略

- broker、paper fill mode、追价 fallback 使用严格枚举。
- IBKR 默认 readonly，追价默认 cancel。
- canonical pipeline 复用唯一 profile strategy 构建入口。
- 策略与风险未知配置显式失败。
- execution/backtest registry 多重匹配时 fail-closed。
- paper 与 IBKR 使用独立账户命名空间。

### 实盘安全

- production demo 数据默认不可用于真实交易。
- preflight 校验数据 provenance、账户身份、权益、可用资金、状态新鲜度和账户归因。
- 每次提交前重读 kill switch、live 开关、readonly、account 和交易日历。
- notional 采用计划金额、参考价和限价中的保守最大值。
- 统一订单状态分类。
- 追价处理撤单确认、部分成交剩余量和未知状态；未知状态停止整个批次。
- IBKR 使用全客户端 API 挂单视图并按目标账户过滤。
- IBKR 成交方向统一，补充 account、execId、permId、clientId、conId 语义。
- 成交以 `broker + account + execId` 唯一持久化，并使用完整账户身份匹配订单。
- 超时撤单按 broker/account/client/order 身份隔离，撤单请求先记录为
  `CancelPrepared`，券商接受后再推进为 `PendingCancel`。
- IBKR 活跃订单缺失真实 orderId 或返回未知状态时 fail-closed；completed
  回调缺失原始 orderId/clientId 时只允许用 orderRef/permId/conId 强身份恢复。
- IBKR `orderRef` 由 `plan_id + attempt_no` 稳定派生。
- 执行批次按 broker/account/profile/strategy/output_asof 稳定派生。
- 每次 attempt 先写 `Prepared`，再以有效租约和 fencing token 原子认领为
  `Submitting`，之后才允许调用券商。
- 相同幂等键的不同请求摘要会 fail-closed；已确认结果只回放，不重复下单或
  重复占用内存风控额度。
- 账户级数据库租约在快照读取前获取，CLI 与 scheduler 共用同一路径。
- instrument registry 覆盖下单、行情、持仓、订单和成交，全部按 conId 对齐。
- 对账合并 IBKR open/completed orders 和 executions，并恢复未知提交及
  `PendingCancel` 终态。
- executions 携带 orderRef；既有 `order_id=NULL` 成交可在强身份恢复后回填
  并生成交易归因，累计成交与剩余量保持单调。
- `CancelRequestFailed` 保持账户级 recovery blocker；终态订单不再创建重复
  撤单意图。
- max-steps、fallback 和限价偏移形成持久化 policy fingerprint；追价启动前
  校验全部 attempt，配置扩张、收缩或语义漂移时在任何券商写操作前阻断。

### 数据库与基础设施

- 修复 `FillRecord.order_id` nullable 漂移，并通过 0015–0017 迁移补充订单券商范围和成交身份。
- 数据库 URL 日志脱敏。
- STARTTLS 失败停止邮件发送，不再明文降级。
- scheduler 使用 profile timezone/calendar，定时报表使用 portfolio 口径。
- 交易结果和 run health 先持久化，告警按 best-effort 处理。

## 剩余风险

### P0 实现状态

以下代码能力已经完成：

1. attempt 级持久化在先、稳定 `orderRef`、请求摘要和数据库唯一约束。
2. `SubmissionUnknown` 禁止重提，并按 open/completed orders 的 `orderRef`
   恢复原记录。
3. `broker + account` 原子租约、TTL heartbeat 和 fencing token。
4. 正式 instrument registry、conId 精确 qualification 和反向映射。
5. completed orders / executions 对账及 `PendingCancel` 终态恢复。

真实资金解锁前仍必须完成：

1. 录入并双人核验目标账户实际使用的 instrument/conId。
2. 将 production 数据切换到可追溯的非 demo 数据，并显式通过 eligibility
   审批。
3. 在 PostgreSQL 上执行多进程并发、租约接管、强杀和恢复测试。
4. 为迁移前 broker 为空的历史订单提供核对与补录工具。
5. 保存空持仓快照批次，避免清仓后读取旧批次。

### P1：可靠性与可维护性

1. 将 `live/service.py` 拆为 `prepare_run`、`preflight_use_case`、`execute_batch` 和 `reconcile_run`，通过 `LiveRunContext` 注入 broker、session factory、clock 和 alert sink。
2. repository 默认 `add/flush`，由应用层 Unit of Work 统一 commit；对账、订单和 run health 使用明确事务。
3. 数据集采用临时文件、完整校验、内容 hash 和原子 rename；manifest 同步发布。
4. 报告按真实日/周/月窗口切片，文件名包含 profile、period、asof/run_id，避免覆盖历史。
5. 把账户健康判定从 reporting 移到 monitoring/risk typed service，报告层只渲染 snapshot。
6. 把日损、drawdown、kill-on-error 等全局风险配置建模并接入 preflight / pre-submit。
7. 在 profile 中显式建模允许下单的 session/window；当前只校验交易日。

### P2：工程化与研究可信度

1. Alembic 成为唯一 schema 事实来源，逐步移除 `create_all + SQLite 补丁` 双轨逻辑。
2. 将 Backtrader/vectorbt 入口改为准确命名，或真正实现独立引擎交叉验证。
3. 建立统一成本、滑点、lot size、现金和成交容量模型。
4. 将 IBKR、Dashboard、PDF、PostgreSQL 等拆为可选依赖组。
5. 把 configs/templates 打包为 package data，并增加 wheel 外部目录 smoke test。
6. 增加 CI：pytest、Ruff、Alembic upgrade、wheel install、最低覆盖率。

## 建议目标架构

保持单体部署，逐步形成以下单向结构：

```text
domain
  common value objects
  strategy / portfolio / risk policies
        ↓
application
  research / backtest / live use cases
  ExecutionCycle / UnitOfWork
        ↓
ports
  MarketDataPort / BrokerPort / RepositoryPort / AlertPort
        ↓
adapters
  parquet / yfinance / IBKR / SQLAlchemy / SMTP
        ↓
interfaces
  CLI / scheduler / dashboard
```

reporting 接收不可变 `ReportSnapshot`；monitoring 接收运行事件；二者不能反向影响订单提交结果。

## 真实资金解锁清单

以下项目全部满足前，保持：

```text
NORTHSTAR_LIVE_TRADING_ENABLED=false
NORTHSTAR_IBKR_READONLY=true
data.live_trading_eligible=false
```

解锁评审至少需要：

- 同一 execution cycle 并发两次，只产生一个 broker intent。
- 在 `placeOrder` 成功后、DB 写入前注入崩溃，重启不会重复下单。
- 所有持仓、订单、成交可用 account + conId + broker identity 唯一对齐。
- 未知提交、撤单未确认、账户不一致、日历不可用均停止整个批次。
- paper soak 覆盖部分成交、断网、重连、人工挂单、清仓和跨日恢复。
- 迁移、回滚、备份和恢复演练通过。

在这些条件完成前，本项目的正确定位仍是“研究与 paper trading 平台”，不是可直接启用真实资金的生产交易系统。
