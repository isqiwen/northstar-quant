# 架构总览

Northstar Quant 当前采用“模块化单体”架构。对个人量化系统而言，这比拆成微服务更容易审计、测试和恢复；当前重点不是增加服务数量，而是保持单向依赖、明确交易边界并让所有外部副作用可追踪。

## 当前主流程

研究与回测链路：

```text
profile / data
  → canonical strategy pipeline
  → portfolio combination
  → risk limits
  → target / simulation backtest
  → reporting
```

paper / live 链路：

```text
CLI / scheduler
  → production profile + market data
  → canonical strategy pipeline
  → broker state + quotes
  → live preflight
  → execution plan
  → pre-trade risk
  → per-submit safety guard
  → OrderRouter
  → Paper / IBKR adapter
  → reconciliation + database
  → run health + alert
```

执行计划不是券商订单。只有通过 preflight、交易前风控和每次提交前安全门禁后，计划才能进入券商适配器。

## 模块职责

- `common`：无业务上游依赖的通用值对象、订单状态和数量规则。
- `config`：运行时 Settings 与交易画像加载。
- `data`：市场数据下载、规范化、存储、校验和 manifest。
- `strategies`：策略注册表与唯一 canonical pipeline。
- `portfolio`：多策略组合和目标权重合成。
- `risk`：风险模型、账户容量预留和交易前检查。
- `backtest`：目标权重回测与策略仿真入口。
- `execution`：执行计划、订单路由、券商端口与适配器。
- `live`：preflight、对账、单轮运行、调度和订单管理。
- `db`：ORM、迁移、会话和仓储。
- `monitoring`：健康检查、运行健康汇总和告警。
- `reporting`：报告渲染、PDF 与邮件发送。
- `research`：研究用例入口。
- `cli`：命令行 composition root。

## 已执行的依赖边界

`tests/test_architecture_boundaries.py` 会检查以下核心约束：

```text
common    → 无内部依赖
config    → common
risk      → common
data      → common, config, logging_
execution → common, config, risk, logging_
db        → common, config, execution, logging_
```

同时，整个 `northstar_quant` 包级依赖图必须无环。当前已消除原有的：

- `db ↔ execution`
- `execution ↔ live`
- `execution ↔ risk`
- `live ↔ monitoring`
- `live ↔ reporting`

相关共享语义已下沉到 `common`，券商基础设施归入 `execution`，对账归入 `live`，运行健康查询归入 `monitoring`。

## 实盘安全边界

真实券商路径默认关闭，并要求同时满足：

- `NORTHSTAR_BROKER=ibkr`
- `NORTHSTAR_LIVE_TRADING_ENABLED=true`
- `NORTHSTAR_IBKR_READONLY=false`
- 显式配置 `NORTHSTAR_IBKR_ACCOUNT`
- production profile
- 数据画像显式 `live_trading_eligible: true`
- manifest 与 profile / dataset 一致，且来源不是 `demo`
- 券商状态账户、权益、可用资金、挂单视图和账户归因完整
- 目标市场交易日可由正式交易日历确认
- 每笔订单通过交易前风险检查和最新 kill switch 检查

任何必需数据缺失都应阻断交易，而不是使用估算值继续。

## 当前架构判断

研究、paper、live 已共享一条策略管线，模块依赖也已实现无环；因此当前最合适的演进方式仍是模块化单体。

真实资金尚未达到可解锁状态。剩余首要缺口是持久化在先的幂等提交协议、跨进程执行租约、完整的 instrument 映射，以及 broker/account 维度的订单与撤单隔离。详见 [架构审核与演进路线](10_架构审核与演进路线.md)。
