# 架构总览

Northstar Quant 是一个面向中国商品期货的模块化单体。它按六个顶层业务领域组织，目的不是把
代码拆成微服务，而是让事实、推断、研究决策、风险决策和真实交易之间保持可审计边界。

平台默认 `paper`，`NORTHSTAR_LIVE_TRADING_ENABLED=false`，且没有 production 画像或真实
CTP 报单适配器。本架构不会改变这些安全前提。

## 六大领域

| 领域 | 源码目录 | 回答的问题 | 当前状态 |
| --- | --- | --- | --- |
| Data Platform | `data_platform/` | 世界和市场有哪些可验证的数据事实？ | 已有行情、合约、质量和 legacy manifest 链路；P1-WP01/02 已完成不可变领域契约与本地制品库，P1-WP03/04 已建立 Contract Master 与离线交易日历边界，P1-WP05/06 已完成预发布质量评估、受控适配器协议和不可变发布链，P1-WP07 已完成行级 PIT snapshot，P1-WP08 已以真实质量引擎完成离线端到端闭环；仓库现有真实来源仍未获授权，不能发布研究或交易数据。 |
| Intelligence | `intelligence/` | 世界发生了什么，为什么可能影响市场？ | P4 已完成 Document→Event、实体消歧、ontology、机制、impact、market context、九个 `intelligence.*` feature 与离线 golden 链路。P10-WP02 已完成六商品的严格 `fixture_only` Document→merge→Mechanism→Impact→Feature-definition golden corpus；P10-WP03 只将其 handoff 用于 fixture-only、逐决策可见性与 synthetic outcome 的研究回放，绝不代表授权市场数据、真实合约或可交易映射。P8-WP02 的 v3 immutable projection 将每条 Event evidence 的 P1 raw artifact/document/content hash/UTF-8 span/receipt 绑定，并将每个 MarketContext 的唯一 P1 normalized artifact、receipt 与全行 commitment 绑定；application 在同一制品库重放验证后，才经 P1 进入 P2 的 `FeatureLineage`/`FeatureBackfill`。它不构成 Research Decision、目标、执行或 broker 能力。 |
| Research & Strategy | `research/` | 什么具有统计价值，怎样形成策略？ | P2 已完成 Dataset→Feature→Experiment→Backtest→Validation→具名批准的 Research Card/Decision 可复现链；当前静态研究仍固定 `decision_time_safe=false` 且不可交易。P10-WP03 另有 `FIXTURE_ONLY_INTELLIGENCE_REPLAY`：它把六个 WP02 handoff、`available_at <= decision_at` checkpoint 和仅事后可见的 synthetic outcome hash-bind 到 Validation/`RESEARCH_ONLY` Card；它不是 DatasetVersion、市场收益或 candidate，P3 activation 会拒绝。P8-WP03 只能由 application 的人工激活边界把精确 `CANDIDATE` 证据链交给 P3 `StrategyTarget` v2。 |
| Portfolio & Risk | `portfolio_risk/` | 应该持什么、持多少、承担多少风险？ | 已实现目标合成、权重分配与研究/预交易风控；`StrategyTarget` v2 必带 hash-only `StrategyTargetActivationRef`，而完整 Research provenance 仍由 application receipt 持有，P3 不反向导入 Research。P10-WP04 新增 strict `CanonicalPortfolioComposer`：它只从多个已激活 source target 的 typed allocation input 内部重放可审计的 `PortfolioTarget v2` / `PortfolioCompositionEvidence`，不接触 approval、ExecutionPlan、订单或 broker。 |
| Trading & Execution | `trading_execution/` | 如何安全地把目标变成真实持仓？ | 已实现 paper/ctp_sim 执行、门禁、订单恢复与对账；真实 CTP 仍阻断。 |
| Platform Foundation | `platform/` | 整个平台靠什么配置、存储、观测和运行？ | 已实现共享类型、配置、数据库、日志、通用可观测性与报告基础设施。 |

`Platform Foundation` 是支撑层，不是串行交易步骤。`Intelligence` 已有受控的静态研究输入接缝，
但它只允许已绑定 P1 raw artifact/document/content hash/UTF-8 span/receipt 的 Event evidence、完整
ontology/mechanism/impact，以及已绑定唯一 P1 normalized artifact/receipt/全行 commitment 的 context，在同一
immutable ArtifactStore 完成 source-artifact 验证与唯一 context DatasetVersion 行回放后，经过明确的 P4→P1→P2
路径进入研究；现有外部来源仍不因该接缝而获得发布、候选准入或交易授权。

`application/` 是根级 composition root：它组装 CLI、回测工作流、运行编排、报告、健康检查
与看板，因而可以调用六个领域。它不是第七个业务领域；任何领域或 `platform/` 都不得反向导入它。

## Data Platform 的不可变制品与领域契约

P1-WP01 在 `data_platform/contracts/data_domain.py` 定义数据事实的稳定值对象，在
`data_platform/artifacts/fingerprints.py` 定义确定性内容指纹。契约覆盖 `DataSource`、
`RawArtifact`、`NormalizedArtifact`、`DerivedArtifact`、`DatasetVersion`、
`DataQualityResult`、`DataLineage` 与 `LicenseMetadata`：每个可发布制品都应携带来源、
schema/transform 版本、内容哈希、provenance、质量结论和上游 lineage，而不是仅依赖文件路径。

时间语义必须区分 `acquired_at`（平台取得材料的时间）与 `available_at`（研究或下游在
point-in-time 条件下可使用的时间）。研究、特征和回测只能消费 `available_at` 不晚于模拟时点
的版本；标准化身份由稳定的规范化输入与内容指纹确定。`NormalizedArtifact` 的确定性工厂会先
校验 raw 字节哈希，再对同一输入执行两次转换；输出不一致即拒绝发布，从而使相同 raw 输入和
transform version 可复现相同 normalized hash。

P1-WP02 在 `data_platform/artifacts/immutable_store.py` 实现本地不可变制品库。它固定使用
`<storage_dir>/artifacts/`，以 SHA-256 派生 blob、snapshot、dataset manifest、normalization binding
和 snapshot-level lineage 的永久路径；发布只会创建新对象或逐字节验证既有同哈希对象，绝不覆盖旧
版本、维护 `latest` 指针或提供自动 GC。它支持 raw / normalized / derived 制品、内容去重、
raw snapshot + transform/schema 到 normalized 内容的唯一绑定，以及按 `DatasetVersion` 完整回放。

该制品库只接受已授权且可审计的来源快照：来源与许可必须 active，具备内部研究用途、合同引用、
条款哈希和有效期；raw/normalized 与 derived 分别需要对应的存储许可，派生制品还会核验所有
上游来源。未知、过期或不允许的授权会失败关闭，不能以本机缓存或旧配置替代。

这不等于现有 legacy 数据链路已经迁移。`storage/downloads`、`storage/market`、`storage.py` 和
`data_manifest_v3` 仍是既有下载缓存/当前市场投影；P1-WP06 的受控发布器不会改写或自动导入其中的
文件。它只能接收实现 `DataSourceAdapter` 协议的 adapter，在获取前后、写 raw 前、写 normalized 前及
释放 `DatasetVersion` 前重新核验当前无密钥授权；未授权的 legacy 下载或市场文件绝不能被误称为
不可变制品库的已发布内容。

## Contract Master：研究序列、实际合约与规则证据

Contract Master 的初始实现位于
`data_platform/contracts/contract_master.py`，并由
`data_platform/contracts/contract_master_loader.py` 严格加载
`configs/instruments/contract_master.yaml`。它是 Data Platform 的中立市场事实模型，不导入
CTP、账户、订单或策略；将已解析的实际合约绑定到某一 broker 身份，只能在
`application/` 与 Trading & Execution 的明确组合边界发生。

```text
Commodity ─┐
           ├── Instrument ── Exchange
           │       ├── ContinuousResearchSeries   # 仅研究/特征/回测
           │       └── Contract                   # 实际月份合约
           │                └── ContractRuleSnapshot
```

这里的 `Commodity`、`Exchange` 和 `Instrument` 是稳定身份；
`ContinuousResearchSeries`（例如 `RB_CONT`）与实际月份 `Contract`（例如 `RB2610`）是不同的
不可变类型。连续序列永远不能被解析器自动换月、自动映射为实际月份合约或变成 broker order
contract。实际 `Contract` 才可附带 `ContractRuleSnapshot`：该快照同时冻结
`observed_at`、`available_at`、有效期、挂牌状态、到期日、乘数、最小变动价位、初始保证金、
开/平/平今手续费、涨跌停、交易会话、交割限制、来源制品哈希、来源权威、质量结论和
`execution_eligible`，并以内容哈希标识。

执行侧必须带显式的 `decision_at` 调用 `resolve_for_execution()`，且只能在返回
`RESOLVED` 后回到同一份 `ContractMaster` 调用 `require_execution_contract()`，重新验证后才可取得
实际 `Contract` 与规则快照。以下任一情况均只返回
不可执行结论，且不携带可供下游偷用的合约或规则：连续序列、未知或歧义映射、规则缺失、
规则在决策时点之后才可用、同一时点存在多份可用有效规则、未挂牌或已到期、交割限制、规则质量不是 `PASS`，
或未明确标为 `execution_eligible`。这是一条 fail-closed 的事实解析边界，不是下单授权。

仓库提交的 `configs/instruments/contract_master.yaml` 只保存商品、交易所、品种和连续研究序列的
静态身份；当前 `contracts` 与 `rule_snapshots` 均为空，静态 loader 也会拒绝非空的
`rule_snapshots`。任何可执行规则快照只能由后续的授权制品发布链生成，不能写回静态 YAML，
而当前尚不存在该发布入口。公开研究行情、产品卡或回测参数不能补全这些动态规则，更不能被当作
真实下单规则。真实 CTP 认证/报单适配器尚未实现，本工作包也没有新增数据库表或 Alembic migration。

## Trading Calendar：离线会话事实与提交门禁

P1-WP04 在 `data_platform/calendars/` 建立了版本化、离线、按交易所和稳定品种精确枚举的
交易日历。`TradingCalendarSnapshot` 保存来源制品 hash、`observed_at`、`available_at`、覆盖范围、
休市日期和绝对时间会话；`CalendarService` 只接受显式 `at` 与 `decision_at`，返回带稳定原因码和
snapshot hash 的 `CalendarDecision`。`OPEN` 是唯一可继续下一道门禁的结论；覆盖不足、未来才可用、
来源质量非 `PASS`、品种会话缺失、重叠或盘外都不会猜测为开市。

夜盘必须以绝对区间保存，并显式写入归属的 `trading_day`。例如周日前夜是否属于下一交易日，
只能由来源快照中的会话决定，不能由“周一到周五”或固定 `21:00` 规则推导。日历中的
`instrument_id` 是稳定品种身份（例如 `SHFE.RB`），不是实际月份 `RB2610`；Application 仅在
`OrderRouter.prepare_order()` 之后，经已启用 CTP 映射把最终实际身份桥接到稳定品种，再进行逐订单
会话判断。最终提交以同一个 `submission_at` 重新读取画像、重验数据治理和券商/生命周期资格，再由
Contract Master 重新解析实际月份合约；订单时点必须同时落在 Calendar Session 与该实际合约
`ContractRuleSnapshot` 的同名规则会话内。该桥接不构成交易授权，也不能替代 Contract Master 的
到期、交割、质量或规则门禁。

仓库只提交 `tests/golden/trading_calendar/` 下的 `test_only` 合成 fixture，用于长假、跨年、夜盘、
早收市和品种差异回放；它不能作为运行时配置。真实日历只能从不可变制品库的 normalized calendar
payload 读取，画像以 `futures.calendar_artifact_snapshot_hashes` 按交易所引用 ArtifactSnapshot hash，
不接受 YAML 路径。每个制品只能绑定一个 Calendar Snapshot，且 record 必须冻结 payload hash、语义
calendar content hash 和直接 raw 来源 snapshot；来源还须与当前受管配置一致、标记为
`authoritative_calendar`，并以有效 live 授权明确覆盖交易所、品种、`trading_calendar` 数据集和
`live` 环境。当前没有这样的来源制品或 production 日历配置，因此空映射、test fixture、来源或内容
绑定缺失都会在调度和券商提交前失败关闭。

## Data Quality Engine：预发布事实评估

P1-WP05 在 `data_platform/quality/` 中将质量判断从 legacy schema 校验中拆成纯内存、可回放的
预发布评估。一次 `QualityRequest` 必须显式绑定候选制品、输入表、`checked_at`、`decision_at`、
政策 ID/版本和完整政策指纹；输入必须同时提供引擎定义的 canonical frame payload，核心会重建该
payload、逐字节比对并验证 SHA-256 等于 Artifact 内容哈希。构造后或 resolver 调用中发生的
Polars 表原地变异均会被拒绝或隔离。它不读取当前时钟、网络、数据库或“最新”市场文件，也不会排序、
补值、截断或修复输入后再宣布通过。

固定规则集为 `completeness`、`uniqueness`、`ordering`、`schema`、`range`、
`calendar_consistency`、`contract_consistency`、`staleness`、`gap` 与 `revision`。每条规则都产生
不可变的 `QualityFinding`，其证据只保存 canonical、无凭据且不含本机路径的结构化摘要；整份
`QualityEvaluation` 以候选 ArtifactSnapshot、时间、规则政策和 findings 计算身份。输入事实、阈值、
日历/合约/覆盖基准或不可变修订基线缺失时，结论必须是 `UNKNOWN`，不能以运行时配置、工作日猜测或
未来修订替代。

日历、合约和缺口适配器只能返回带 `available_at` 与不可变 `reference_hash` 的事实，且该时点必须不晚于
`checked_at`；任何未来可见的引用都会使对应规则失败关闭。`gap` 必须给出覆盖窗口，逐分组检查首尾和
内部区间；`schema` 同时绑定预期 Artifact schema version，额外列必须明确允许。`revision` 只比较调用方
显式提供、PIT 可见且质量/来源/schema/transform/kind 兼容的 prior immutable baseline，因此未来数据修订
不会倒灌旧评估。`QualityEvaluation.require_eligible()` 对 `FAIL` 一律拒绝，对生产所需关键规则的 `UNKNOWN`
一律拒绝；`WARN` 和非关键 `UNKNOWN` 是否允许必须由调用方显式声明，绝不依赖隐式默认值。

评估本身不会改写已经声明为 `PASS` 的 Artifact。若需要生成既有 `DataQualityResult`，调用方必须以相同
内容、来源、schema、transform 和 PIT 身份重构待发布制品，且其聚合 `quality_status` 与评估一致、并且
不得优于候选制品已有状态；否则绑定会失败。P1-WP06 的 `DataSourcePublisher` 自行执行质量引擎，随后把
`PublishedQualityAssessment`、最终 snapshot 的唯一 binding 及完整无密钥 `PublicationAuthorization` 收据
追加式写入 `ArtifactStore`；`DatasetVersion` manifest 精确引用这些证据。质量为 `FAIL` 的 normalized
制品可以保留为审计证据，但不能释放为研究数据集。现有 AKShare、本地导入和采购候选来源均未获此授权，
仍在 fetch 前失败关闭；它们的 legacy 缓存也不会被发布器读取。

## 行级市场数据 PIT Snapshot

P1-WP07 在 `data_platform/market/pit.py` 把制品级 `available_at` 扩展为行情行级事实：
`MarketDataPITSpec` 显式列出主键、事件时间、行级可用时间和全部值列；未声明列不能悄悄流入
回测。`MarketDataPITSelector` 只消费一份明确的 immutable `DatasetVersion`，并要求其 normalized
制品质量为 `PASS`、带不可变 `PublishedQualityAssessment` 与 `PublicationAuthorization`。授权收据
的 hash 和完整脱敏 scope 会一并冻结进 snapshot/回测 manifest；历史回测入口还会严格要求
`purpose=historical_backtest`，并核对市场、资产类别、频率、实际合约数据语义，以及画像品种池
对应的产品/交易所覆盖，不能把仅限 `internal_research` 或只覆盖部分品种的制品扩展为回测用途。每行
`available_at` 必须不晚于该制品本身可读取的时间；相同逻辑主键在同一可用时间出现不同内容、
future row、缺少授权或质量证据、schema 不一致都会失败关闭。

选择器以调用者给出的 `as_of` 选取当时唯一可见的修订，并生成包含 DatasetVersion、来源 snapshot、
PIT spec、revision IDs、授权 scope 和 canonical frame hash 的 `MarketDataSnapshot`。快照不保留可变 DataFrame；
每次读取都会从 canonical bytes 重建并校验身份。新版本的数据修订必须发布到新的 DatasetVersion，
不会覆盖或改变旧版本的回放结果。`application/backtest.py` 在运行前会用同一 selector 重新计算
传入 snapshot，避免手工拼装的 frame 或 manifest 绕过不可变证据链。

当前快照明确标为 `STATIC_AS_OF_VIEW_NOT_DECISION_REPLAY` 且 `decision_time_safe=false`：它可冻结单一
研究输入并重放旧结果，但**不能**证明完整历史回测的每一个决策时点均无未来数据。P2-WP05 的
`research/validation/lookahead.py` 已建立显式逐决策 replay plan：签发前必须从 immutable
`ArtifactStore` 重新选择每个 snapshot，并检查提交的特征、合约/费率规则、事件和目标证据是否晚于
对应决策时点；手工 `MarketDataSnapshot`、篡改 report 或静态 FeatureBackfill 都不能通过这层重算。

当前 `LookaheadCertificate` 仅是**证据一致性回执**，固定
`decision_time_safe=false`、`candidate_admission_eligible=false`。`application/decision_replay_backtest.py`
额外提供了一个刻意收窄的 target producer：只允许 `cn_futures_daily_trend_offline` 的单一内建
`futures_trend`，每个 checkpoint 都要显式声明使用的 `decision_event_time`，从 `ArtifactStore` 重放
当期历史前缀后只保留该时点的 target slice；早期 warmup 只能显式标记为空，不能用未来 target 填补。
轨迹冻结每期市场 snapshot/revision、策略参数，以及信号变换、策略基类、组合/分配/风控和该
composition root 的完整本地代码闭包与 `uv.lock` 依赖摘要、target hash，但同样固定不可准入，且不会调用
现有回测器、Research Admission 或任何交易入口。

仓库尚无受控逐 checkpoint 的特征、事件和带历史可用时间的 Contract Master/规则发布器，因此该轨迹不能
证明完整真实策略输出无前视，也不能进入 Research Admission、候选策略或交易路径。未来严格 Application
编排必须从所有受控 producer 重放并验证完整输入/输出后，才可引入可准入的逐决策证书；调用方手写的安全
布尔字段始终不可信。现有 static/legacy 路径继续被阻断于候选策略之外，且没有被该基础合同升级。
`storage/market`、`data_manifest_v3` 和未授权来源均不允许作为 selector 的回退输入。

## Feature Registry：版本、血缘与受控回填

P2-WP01 在 `research/features/` 建立了 `FeatureSpec`、`FeatureVersion`、`FeatureDependency`、
`FeatureDatasetEvidence`、`FeatureLineage`、`FeatureValue` 与 `FeatureBackfill`。Spec 明确输入列、
实体键、事件/可用时间列和缺失语义；Version 冻结 spec hash、实现 hash、代码 revision 与参数合同。
每条数据依赖保存可重建的 P1 PIT spec、DatasetVersion、snapshot、revision、来源可用时间、授权和
scope 证据，而不是只保存一个数据集名称或裸哈希。

`FeatureRegistry` 自持 `ArtifactStore`：创建 lineage 和物化回填时都会重新通过
`MarketDataPITSelector` 回放上述证据，并精确核验 schema、输入列、实体键和时间字段。计算实现必须
先以相同的 `FeatureVersion` 与 `implementation_hash` 登记为 `FeatureComputer`；Registry 以同一份
已验证快照执行两次，任何结果不一致、实现身份改变、未登记 lineage 或覆盖既有 backfill 的尝试都会
失败关闭。直接构造领域值对象不构成可发布或可消费的研究证据。

当前能力有意收窄为一个单一静态 as-of 输入：`FeatureLineage` 和 `FeatureBackfill` 固定
`STATIC_AS_OF_VIEW_NOT_DECISION_REPLAY` 与 `decision_time_safe=false`。它们不能作为候选策略、生产
资格或逐决策无前视证明；P2-WP05 的基础 Guard 会明确拒绝把它们包装成逐决策特征证据。
受控逐 checkpoint Feature producer、feature-to-feature/multi-input 血缘、持久化特征制品以及
Experiment/Backtest/Research Admission 的严格集成仍留给后续 P2 工作包。`implementation_hash` 代表
受信任构建与代码审查身份，不是执行不受信任 Python 代码的沙箱。

## Intelligence-to-Research Feature Projection：受控静态接缝

P8-WP02 建立的唯一情报到研究接缝严格为：

```text
Event / evidence (P1 raw artifact + document/content hash + UTF-8 span)
/ ontology / mechanism / impact / market context
+ one normalized P1 context artifact + full closed-row content commitment
→ P4 immutable static projection
→ application-owned same-store source-artifact verification + one context DatasetVersion artifact/row replay
→ closed P1 schema: provenance + 9 scores + paired restricted missing reasons
→ DatasetVersion / PIT snapshot
→ P2 FeatureLineage / FeatureBackfill (exact FeatureVersion binding)
```

P4 `intelligence_feature_projection_v3` 绑定精确的 Event、evidence、完整 ontology 内容与版本、机制、
impact、市场上下文和 `available_at`；它是版本化、不可变且静态的。每条 Event evidence 都固定其精确 P1
raw source artifact snapshot、document ID、content SHA-256 和 UTF-8 span，故 source receipt 不能单独伪造
已保存的文档证据。每个 MarketContext 都固定恰好一个 immutable normalized P1 artifact、context
`DatasetVersion`/receipt，以及完整闭合 normalized row 的 content commitment。`application/` 是唯一可把其
最窄 feature-input 表交给 P1 `DataSourcePublisher` 的组合层：它必须在与发布器相同的 `ArtifactStore` 中逐条
解析并核对 source receipt/raw artifact/document/content/span 的绑定及受限研究 scope/时间；随后回放指定
context `DatasetVersion`，要求其中恰好一个 normalized artifact 绑定指定 receipt，并重建其完整 context 行以
核对 commitment、identity 与 PIT。P1 仍独立执行来源、质量、授权与 immutable-artifact 门禁，且 schema
不允许额外列。P2 因而只看到 P1 的 PIT snapshot、九个受限数值与成对的受限缺失原因、以及狭窄的
hash-only provenance，绝不看到原始 Document、URL、正文、source/context payload、evidence 文本或 LLM
rationale。P4 不反向导入 Research；精确 feature 定义/`FeatureVersion` 绑定从 P2 的
`FeatureLineage`/`FeatureBackfill` 开始。任何身份、ontology、receipt、scope、context、质量、语义或 PIT
未知、不匹配或未来可见均失败关闭。

这不是情报到交易的捷径：结果固定 research-only/non-tradable，且仍是
`STATIC_AS_OF_VIEW_NOT_DECISION_REPLAY`；它不提升 Research Decision，不生成 `StrategyTarget`、
`PortfolioTarget`、`ExecutionPlan` 或 `BrokerOrder`，也不接触 broker。授权、身份、semantic type、
`available_at`、PIT snapshot 或任一上游绑定缺失、未知、不匹配或未来可见时均失败关闭。该已验证的
P4→P1→P2 接缝不表示任何现有外部情报来源已经获得生产发布或交易授权。

P10-WP02 的
[`six_commodity_fixture_only_v1.json`](../tests/intelligence/golden/six_commodity_fixture_only_v1.json)
和严格 loader 仅作为版本控制的测试语料：六条链使用 `https://fixture.invalid/` 来源、`fixture-*`
identity、全部关闭的授权标记以及测试专用的 typed crosswalk。它重放 Document→Event→多来源 merge→
Mechanism→Impact，并以 Event/evidence/ImpactPath/FeatureVersion 的稳定 hash 仅交接已注册的
`intelligence.*` Feature **定义**；它不会构造
`AuthorizedMarketContext`、`EventEvidenceAvailability`、P1 发布制品、真实 Contract Rule、日历、
目标或订单。P10-WP03 已在同一 fixture-only 语义内完成六 handoff 的逐决策可见性 replay：它以
`available_at <= decision_at` 选择 observation、以独立且决策后才可见的 synthetic outcome 评估 alignment，
并只生成 `RESEARCH_ONLY` Card。它不会成为 P1 immutable artifact/receipt/context provenance，也不能变成
`FeatureValue`、DatasetVersion、candidate、StrategyTarget 或订单；真正受授权的 feature projection 仍由 P8
接缝约束。

## Research Candidate-to-StrategyTarget Manual Activation：人工、可审计但非执行的接缝

P8-WP03 的唯一跨域组合边界是
`application.research_strategy_activation.ResearchStrategyTargetActivator`：

```text
PASS + named CANDIDATE Research Card / Decision
+ exact ExperimentSpec / ExperimentRun / Dataset / Feature / StrategyVersion
+ exact StrategyTargetProposal
+ named HumanStrategyTargetActivationApproval
→ hash-only ResearchStrategyActivationReceipt + StrategyTarget v2
```

它重放 Research Card、Validation、ExperimentSpec/Run 和 StrategyVersion，再交叉验证完整的
Dataset/Feature/Backtest/Decision 身份。独立的人工 activation approval 必须精确绑定 proposal、card、
decision、experiment spec 与 strategy version，并强制
`input_as_of ≤ candidate approval ≤ proposal generated_at ≤ manual approval < effective_at < expires_at`。
任何缺失、未知、篡改、非 `CANDIDATE`、非 PASS 或未来可见 feature input 都失败关闭。回执固定
`STATIC_REPRODUCIBILITY_ONLY`、`decision_time_safe=false` 和 `eligible_for_trading=false`；它既不是
`PortfolioTarget`/风险批准，也不是 `ExecutionPlan`、broker order 或 AI Tool API capability。

`StrategyTargetActivationRef` 刻意只是 P3 可持有的最小 hash-only commitment，不是可信存储或认证边界；
因此直接构造的 P3 target、手写 hash 或同进程对象不能证明 Research provenance。P8-WP04 现由
`application.execution_provenance_preflight.ExecutionProvenancePreflight` 重新执行每条 activation request
并精确匹配 claimed receipt，再将 exact source-target set、结构化 P3 risk evidence、PIT data evidence、
account/position/quote/contract-rule evidence 和 P5 plan/runtime-risk/preflight 绑定为一个 hash-only receipt。
它不接受调用方注入的 `ExecutionPlan` 或 `PreflightResult`，却仍不会提交订单；旧 P5 `StrategyTarget` E2E
已由 P8-WP05 的 guarded candidate executor 完整替换。

该 receipt 只允许 `ctp_sim`、要求 `NORTHSTAR_LIVE_TRADING_ENABLED=false` 和未启用 kill switch，且其
`eligible_for_ctp_sim`、`eligible_for_trading`、`eligible_for_live` 始终为 `false`。P2 静态证据的
`decision_time_safe=false` 保持不变；P8-WP04 因而只验证 provenance/preflight 证据，不能把候选升级为
订单授权。P8-WP05 的 `application.ctp_sim_candidate_execution.CtpSimCandidateExecutor` 是单独的
CTP-sim-only composition root：它从原始 request 重取可信 simulator state/quotes 并重放证据后才构造 order，
将每个 `plan_hash + order_hash` commitment 与 durable intent 在同一 PostgreSQL 事务一次性消费；只有该
composition root 能签发不透明的 `CtpSimSubmissionAuthority`，结构相同的 guard 不能成为提交能力。
`CtpSimBrokerAdapter` 在自身状态锁内再次验证 consumption 与真实 state/quote 基线，并且每个已成功提交的
batch leg 才能推进该基线。无 authority raw adapter、direct durable 以及 legacy live-service CTP-sim submit
都失败关闭；对账强制从 simulator 读取，缺少消费的 order/fill 会触发粘性 `HALT`。隔离 PostgreSQL 的
candidate→activation→P3 risk→provenance→durable→fill→reconciliation（含双合约 batch）E2E 因而将
`Portfolio/Risk→CTP sim` 标记为 `VERIFIED_SIMULATION`；这只表示候选证据闭环，所有 receipt/matrix eligibility 仍为
false，绝非真实 CTP 或实盘权限。

P10-WP05 在该 P8 consumer seam 加入了独立的 durable manual-risk approval record，但它的状态严格是
`VERIFIED_SIMULATION`：P3 的 `RiskApprovalAttestation` 是纯领域、可重放的 claim，绝不是人工身份凭据。
只有 session-backed、隔离 PostgreSQL 的 CTP-sim candidate 能消费该 account/profile/broker scoped grant；它在
prepare、prevalidate 和 adapter 最终锁内 fence 都重新派生并精确匹配 P3 approval/evidence、authority/policy/
reconciliation、binding 与 record hash。production public composition 没有 approval issuer 或 verifier injection
surface。已认证的外部人工 issuer 与 PostgreSQL 权限分离（candidate 对该 grant 表只读、独立 issuer 写入）仍是
`BLOCKED_EXTERNAL`；因此当前仓库没有生产签发路径，也不会授予真实 CTP 或 live authorization。

## Canonical Multi-Strategy Portfolio Composition：P3 内部、可重放且非审批

P10-WP04 的 `portfolio_risk.portfolio.composition.CanonicalPortfolioComposer` 只接收至少两个
精确重放的已激活 `StrategyTarget` 所在的 `StrategyAllocationInput`，再在 P3 内部调用 allocation core：

```text
exact activated StrategyTarget × N
+ explicit AllocationPolicy / StrategyAllocationInput
→ deterministic allocate()
→ per-source weighted contribution
→ canonically netted PortfolioTarget v2 + PortfolioCompositionEvidence
```

它拒绝 caller-supplied aggregate target/positions/`AllocationResult`，拒绝 target hash、target id、source
strategy 或 activation 的重复，也拒绝 source 尚未在组合生成时生效、输出窗口超出 source 有效期、任一
replay/hash/source-set 不一致。输入按 source target hash、输出按 instrument id 规范排序；未分配现金、零
allocation 和净额抵消后的零仓位均保留并进入 hash，绝不以归一化、截断或丢弃 cancellation 的方式增加风险。

`PortfolioTarget v2` 将 `composition_hash` 纳入 target identity，完整 `PortfolioCompositionEvidence` 再绑定
policy、source snapshot、allocation、pre-net contribution 和净仓位。因此不同 allocation 即使偶然得到相同
net positions 也不会共享 target identity。旧 `portfolio.multi_strategy` Polars/DataFrame 路径没有被此契约
调用。该产物固定 `eligible_for_portfolio_approval=false`、`eligible_for_execution=false` 与
`eligible_for_broker_order=false`；它不是 `ApprovedPortfolioTarget`、ExecutionPlan、订单或 broker capability。
P10-WP05 才能在其基础上派生 portfolio-wide exposure、limits、stress、account risk-state evidence 和审批。

## Canonical Portfolio-Wide Risk Evidence & Approval Gate：P3 派生与受控 CTP-sim authority

P10-WP05 在 P3 建立 `PortfolioRiskApprovalGate`。它只从精确重放的
`PortfolioCompositionEvidence`、账户/合约/风险状态快照和版本化 policy 派生 review；调用方不能把预先算好的
exposure、`RiskMeasurements`、limit/stress check、`PortfolioTarget` 或 approval hash 当作输入塞过门禁。P3 的
纯领域模型本身不读取配置、数据库或 broker，也不把同进程对象当作可信来源；因此它的输出是可重放的风险证据，
而不是账户、市场或提交 authority。

```text
exact PortfolioCompositionEvidence
+ application-owned PortfolioRiskApprovalAuthority
  ├─ complete profile portfolio_risk_approval policy / taxonomy / CTP-sim rules
  ├─ CTP contract registry 的 symbol → instrument / product / exchange / multiplier 映射
  ├─ fresh, complete CTP-sim BrokerStateSnapshot
  │  └─ only NetLiquidation (equity) + AvailableFunds (margin capacity)
  └─ hash-verified persisted reconciliation safety state == NORMAL
→ P3 PortfolioRiskReview
→ PASS + exact named RiskApprovalAttestation
→ ApprovedPortfolioTarget v2
→ P8 non-submitting provenance receipt
```

`application.portfolio_risk_authority.PortfolioRiskAuthorityResolver` 是上图的唯一 authority
重建点。它要求活动画像提供无 runtime default 的完整 `portfolio_risk_approval`：policy id/version、九项
limits、freshness、精确 taxonomy、以及与 taxonomy 产品集合完全相同的 `ctp_sim_execution_rules`；policy version
必须等于 `versions.risk_policy`。它从受控 registry 取实际合约 identity，从 profile 的 simulator-only rule
取 margin rate/max lots，并要求 P5 的 execution rule evidence 精确匹配。账户容量只能来自完整且新鲜的
CTP-sim `BrokerStateSnapshot` 中的 `NetLiquidation` 和 `AvailableFunds`，不会退回到 Balance、Cash、
BuyingPower 或调用方声明值。

在 session-backed CTP-sim candidate 路径中，对账安全状态同样不是调用方可选字段：该路径只会从 account/profile/
broker scope 一致、state hash 可重算的持久化记录重建 authority 输入。首次 `NORMAL` 仅可在一次干净 reconciliation
成功时写入；缺失状态不是 NORMAL，已有
`LIMIT_ONLY`/`REDUCE_ONLY`/`HALT`/`MANUAL_RECOVERY` 也绝不自动恢复。配置、版本、taxonomy、registry、完整快照、账户、时钟、
reconciliation state、hash 或 P5 contract rule 任一缺失、漂移、过期、未来可见或不匹配时，CTP-sim 路由不得
签发 P8 receipt、plan、durable intent 或 simulator mutation。

在得到 authority 对应的精确 P3 request 后，gate 重放组合并派生 gross/net exposure、position notional/margin，
以及恰好九项 `RiskMeasurements`/limit checks：`per_contract`、`per_commodity`、`per_sector`、
`per_exchange`、`per_strategy`、`per_account`、`gross_leverage`、`net_leverage`、`margin_utilization`。它还要求
每种压力场景恰好一次，并同时检查 loss 与 stressed-margin：`gap`、`limit_move`、`volatility_shock`、
`liquidity_collapse`、`correlated_commodity_shock`、`margin_increase`、`fx_shock`。UNKNOWN、未来/过期/陈旧输入、
非 `NORMAL` risk state、任何 WARN/BLOCK、缺失覆盖或 hash replay 不一致都会得到不可批准的 evidence；不能由
attestation 覆盖。

只有 PASS review 的精确 `review_hash` 才能由具名 `RiskApprovalAttestation` 在其输入有效窗口内确认，并构造
account-scoped `ApprovedPortfolioTarget v2`。review、approval evidence 和 target 都固定
`eligible_for_execution=false`、`eligible_for_broker_order=false`。P8 在受控 CTP-sim 路径还必须重新解析
authority，并将 authority/config/policy、broker snapshot、reconciliation state、P3 evidence、P5 contract rules
和 plan hash 一同绑定到 `ExecutionProvenancePreflightReceipt`；该 receipt 的
`eligible_for_ctp_sim`、`eligible_for_trading`、`eligible_for_live` 始终为 `false`，不携带 submit、cancel、
router、database 或 broker capability。

具名 `RiskApprovalAttestation` 仍只是一条 P3 claim，不能因其字段完整就证明人工审批。P10-WP05 的
`PortfolioRiskApprovalRecord` 将已验证的 binding、P3 evidence、authority/policy/reconciliation、approver/
verifier receipt hash 和时间窗作为不可变 PostgreSQL grant 保存；它只用于隔离 CTP-sim candidate 的
`VERIFIED_SIMULATION` 边界。candidate 在 prepare、prevalidate 和最终 adapter fence 都必须重新计算并精确匹配
该 scoped grant 的 hashes，缺失、过期、漂移或篡改一律失败关闭。当前 production public composition 不提供
issuer/verifier 的成功签发路径；接入已认证外部人工 issuer，并把 grant 表写权限与 candidate 的只读权限分离，仍是
`BLOCKED_EXTERNAL`。这不是人类认证的替代，也绝不提供真实 CTP、真实账户或 live authorization。

本地 simulator 的状态改变只能由独立的 `CtpSimCandidateExecutor` composition root 在新鲜 simulator
state/quotes、reconciliation、authority 与短期 receipt 全部重放后进行；每一笔精确 order commitment 需先与
durable intent 一次性消费，adapter 锁内再核对 consumption 与 state/quote 基线。它仅覆盖隔离的
`ctp_sim`、保持 live disabled 与 kill switch 门禁，绝不使上述 profile policy、fixture、receipt 或测试成为真实
CTP、production profile、授权实时数据或实盘资金权限。

P2-WP02 在同一受控 catalog 中登记九个 feature family。每个 computer 只读取 P1 的 immutable

| Feature | 输入 contract | 要点 |

Contract Master：当前静态 Master 没有实际合约，未来 Data Platform 投影必须建立该成员关系。

除上文 P8-WP02 的 `intelligence.*` 静态 projection 接缝外，这些 schema 目前仍只是 Research consumer

发布同样不表示外部来源已获授权，也不改变静态、不可交易的边界。特别是 curve/basis 的 `available_at`
只表示制品可被下游读取的时间，**不等于**报价对齐事实；真实使用前必须由 Data Platform 发布可审计的
报价/对齐制品。九个 feature 的当前结果一律是 `STATIC_AS_OF_VIEW_NOT_DECISION_REPLAY`、
`decision_time_safe=false`，不能进入候选准入、生产资格或交易。

## Experiment Registry：静态可复现账本，不是策略审批

P2-WP03 在 `research/experiments/` 建立 `ExperimentRegistry`、`ExperimentSpec`、`ExperimentRun`、
`StrategyVersionReference` 和逐特征的 `ExperimentFeatureInput`。Registry 只能通过 `FeatureRegistry`
的精确只读入口取得已经物化的 `FeatureLineage`/`FeatureBackfill`；每一项实验输入保留其
DatasetVersion、PIT spec/snapshot/revision、来源可用时间、授权 scope 与 evidence hash 的对应关系，
而不是只保存一个“最新数据集”名称。

同一个 Experiment 的所有输入必须使用相同的 static `as_of`，并与策略和所有 FeatureVersion 的
`code_revision` 精确一致；train、validation、OOS 日期段严格按顺序且不重叠。Spec 的内容 hash
不包含展示性 `experiment_id`，Registry 会拒绝以不同 ID 重复登记同一实验内容。成本、滑点和参数
仅允许扁平的有限标量；路径、凭据、原始表格/特征值结构以及任意运行时对象都会失败关闭。

`ExperimentRun` 只保存 runner、配置、结果和证据的 SHA-256 引用，不保存 DataFrame、回测曲线、
原始制品或审批状态。Spec/Run 固定为 `STATIC_REPRODUCIBILITY_ONLY`、`decision_time_safe=false`、
`eligible_for_backtest=false`、`eligible_for_admission=false`：它们不能触发 backtest、候选策略准入、
Research Decision 或任何交易路径。当前 `StrategyVersionReference` 仍是声明性构建身份，运行引用
也尚未持久化；不可变 StrategyVersion、真实 BacktestRequest/Result、逐决策 PIT 和 Validation 留给
后续 P2 工作包。

## 统一回测合同：审计一致，不等于成交同质

P2-WP04 在 `research/backtest/models.py` 定义不可变 `BacktestRequest`、`BacktestResult` 与
`RunManifest` v4。唯一编排入口先冻结 profile、策略目标、数据/PIT evidence、频率链、成本假设和
代码工作树身份；报告只能接收已验证的 `BacktestRun`。正式制品不记录墙钟生成时间，复用时会从
冻结运行重建完整 Markdown/JSON 并逐字节比对，而不是信任文件内自报的 checksum。手拼 manifest、
联动篡改既有报告/自报 hash，或运行时替换内置回测器都会失败关闭。

| 引擎 | 可诚实主张的能力 | 不能主张 |
| --- | --- | --- |
| `weight_return` | 连续研究序列的延迟权重、收盘收益与成本近似 | 实际合约、订单、成交、保证金、换月或流动性 |
| `futures_daily` | 实际合约逐日状态机、保守 OHLC、费用、保证金、换月与模拟成交事件 | 日内路径、tick/L2 队列或完整订单生命周期 |
| `futures_intraday_replay` | 分钟级盘口/参与率/队列假设下的订单、部分成交、撤单和保证金回放 | 交易所逐笔/L2 精确队列、隐藏流动性或网络延迟 |

`RunManifest` 记录的是研究审计证据，不是策略批准。无论上游研究准入规则给出什么观察值，P2-WP04
输出都固定 `candidate_admission_eligible=false` 和 `research_admission.status=NOT_ELIGIBLE`；原始政策
观察值仅在 `observed_policy_status` 中保留。legacy `data_manifest_v3` 与当前
`STATIC_AS_OF_VIEW_NOT_DECISION_REPLAY` 仍不是逐决策 PIT 证明；当前 P2-WP05 的基础 Guard 也不会将其
升级为安全回测，完整受控逐决策编排、验证和 Research Decision 仍是后续工作。

## Data Platform 离线端到端闭环

P1-WP08 的集成测试以测试内合成、受控授权来源验证 `Source → Raw → Normalize → Validate →
DatasetVersion → Research Consumer`。adapter 只从不可变 raw bytes 重新解析标准化表，发布器对同一
raw 双执行 normalize，真实 `DataQualityEngine` 必须产生十项 `PASS` findings，随后才能写入质量
sidecar、授权收据和 DatasetVersion。测试再通过 PIT selector 调用真实研究回测入口，并在 run manifest
中保留 DatasetVersion、授权范围和静态 PIT 身份。该测试完全离线、不连接数据库或券商；合成授权绝不
代表现有 AKShare/local 来源获得发布或交易授权。

## 业务闭环

```text
Market ──事实数据、订单回报、成交与结算──> Data Platform
                                               │
                                               ▼
                                        Intelligence
                                               │
                                               ▼
                                   Research & Strategy
                                               │
                                               ▼
                                    Portfolio & Risk
                                               │
                                               ▼
                                   Trading & Execution
                                               │
                                               └──────────────> Market
```

领域之间传递的不是模糊的字典，而是有版本、来源和时间语义的内容：

1. Data Platform 发布经 schema 与质量检查的数据制品和市场/合约事实。
2. Intelligence 将外部材料归为事件、实体和影响上下文；P8-WP02 仅把已绑定 P1 raw
   artifact/document/content/span 的 evidence、ontology/mechanism/impact/context，以及单一 P1 normalized
   context artifact 的全行 commitment，作为静态 projection 经 application-owned P1 发布和 PIT 交给 P2
   形成 FeatureLineage/FeatureBackfill，绝不直接形成策略、目标或订单。
3. Research & Strategy 从事实生成特征、策略输出、回测证据和具名 `CANDIDATE` 研究结论；它本身不生成
   可执行目标。
4. `application` 仅在独立具名人工 activation 与完整身份/PIT 重放后，才签发不可交易的 `StrategyTarget` v2
   receipt；该 receipt 不等于组合或执行批准。
5. Portfolio & Risk 在 P3 内合成策略目标、应用资金分配和风险限制，产出受约束目标。
6. Trading & Execution 在 preflight、运行时风控和预交易检查全部通过后，才把计划提交给
   broker；订单、成交、对账和结算结果必须重新成为可审计事实。

执行计划不是券商订单。任何必要数据、授权、合约身份、风险结论或账户状态缺失时，交易路径
必须失败关闭，不能用旧快照、连续合约 symbol 或估算值替代。

## 跨平台与 Linux 运行边界

“跨平台”不是要求每台机器都承担同样的运行职责。Windows 和 Linux 都是一级开发工作站，
用于可重复的研究、回测、测试、CLI、配置和制品操作；Linux 才是服务与未来实时交易的唯一
目标平台。

| 范围 | Windows 开发机 | Linux 开发机 | Linux 生产服务器 |
| --- | --- | --- | --- |
| Data Platform / Intelligence Core | 支持 | 支持 | 作为应用依赖运行 |
| Research / Features / Strategy / Backtest | 支持 | 支持 | 可读取已发布制品，但不把研究任务当作服务调度器 |
| Portfolio & Risk Core | 支持 | 支持 | 为受控执行路径提供约束 |
| CLI、开发脚本、制品构建 | 支持 | 支持 | 只运行已发布版本所需的 CLI |
| PostgreSQL integration、迁移、完整 pytest | 不在默认 Windows CI 中运行 | 支持 | 仅部署/运维流程按需执行 |
| systemd、服务、scheduler、worker、目标监控 | 不支持也不模拟 | 不作为默认开发职责 | 唯一运行位置 |
| future live trading | 不支持 | 不支持 | 仅在所有生产门禁完成后才可启用 |

```text
Windows 开发机 ─┐
                ├─> just ─> Python 控制面 ─SSH─> Linux 目标端操作
Linux 开发机 ───┘       （预检 / 制品 / 清单）     （systemd / 权限 / 发布）
```

`just` 是第一层命令路由；`scripts/dev/*.py`、`scripts/deploy/*.py` 与 `scripts/ops/*.py`
是第二层跨平台控制面；`scripts/*/remote/linux/`、`infra/systemd/` 与可选 Docker 运行时属于
第三层 Linux 目标操作。Python 控制面默认不应因为在 Windows 上运行就要求 systemd 或本机 Linux
服务；Linux 目标端也不得信任客户端检查，必须重复执行 production、broker、preflight、kill switch
及权限门禁。

## 依赖边界

六个领域的正常依赖方向为：

```text
Trading & Execution → Portfolio & Risk → Research & Strategy
                     → Intelligence → Data Platform → Platform Foundation
```

这不是仅靠约定维持的图：`tests/architecture/` 使用 AST 同时解析绝对与相对导入，并阻断：

- `platform` 对任一业务领域的依赖；
- Data Platform 对研究、组合、执行的依赖；
- Intelligence 对执行的依赖；
- Research 对 broker 或执行的依赖；
- Portfolio & Risk 对 live orchestration 或执行的依赖；
- 领域间循环，以及任何领域反向导入 `application/`。

`application/` 是唯一允许跨领域调用的组合层；它只消费领域公开能力，绝不成为领域模型、
策略、风险决策或订单状态的归属地。`platform/db` 仅提供表、会话和基础持久化能力，不负责
策略、风控或订单决策。

## 研究、账户与交易路径

研究与回测不读取账户，也不提交订单：

```text
交易画像 + 已验证数据制品
  → 策略输出 + 组合风险约束
  → profile-selected backtest engine
  → immutable run manifest + report
```

账户路径必须在合格画像中经过完整门禁：

```text
冻结目标
  → 最新账户 / 行情 / 风险状态
  → preflight
  → execution plan
  → pre-trade checks
  → CalendarDecision（最终实际合约的明确会话）
  → broker adapter
  → reconciliation + audit records
```

`paper` 和本地 `ctp_sim` 仅用于工程与语义演练。真实 `CTPBrokerAdapter`、production
画像、经授权实时数据和期货公司模拟前置演练均未完成，因此真实资金路径仍被阻断。完整条件见
[执行与安全边界](03_执行与安全边界.md)。

## 平台消息通知

`platform.messaging` 提供一版受限的进程内 FIFO 通知队列。它只接受版本化、不可变的
`MessageEnvelope` 和预注册 topic（数据、情报、feature、研究、组合、风险、订单状态和对账失败）。
消息处理失败时，消息保留在队首并阻止后续消息越过；显式重试可能重复投递，因此消费者必须按
`message_id` 幂等。主题在发布前必须已有消费者，否则发布直接失败，不会伪装为已投递。

该队列不是 durable broker、事务外盒或订单路由器：进程重启不会保存消息，且它绝不产生
`ExecutionPlan`、不提交订单、不放行风险或绕过 pre-trade gate。未来如需跨进程/持久化消息能力，
必须新增独立 work package，并保留这些安全边界。

## 平台调度

`platform.scheduling` 以 `ScheduledJob` 和 `JobRegistry` 定义数据、情报、feature、研究、维护和
live 六类作业的统一注册合同。具体任务只能由 `application/` composition root 绑定到 APScheduler；
Platform 本身不导入领域任务。`LIVE` 类作业必须携带 lifecycle gate，且 gate 先于 action 执行；
任何 calendar、profile、broker 或风险 gate 异常都会阻止 action，不会被调度器吞掉或改为执行。

现有日频执行作业已通过此合同绑定期货会话 gate。调度触发只是候选时点，不会替代 profile、日历、
preflight、plan gate、broker capability 或 kill switch；数据/情报/feature/研究/维护作业在接入时也
必须通过同一 typed registry 注册，不能旁路添加未声明作业。
