# 执行与安全边界

本文只描述当前可运行的执行基础设施和明确阻断项。研究与回测边界见
[期货回测器说明](04_期货回测器说明.md)，阶段升级条件见
[项目主规划与实施状态](08_项目主规划与实施状态.md)。

## 当前状态

| 路径 | 当前用途 | 明确不代表 |
| --- | --- | --- |
| `offline` | 历史研究、回测和报告 | 账户、订单或真实交易资格 |
| `paper` | 通用订单持久化、账本、对账和报告基础设施验证 | 期货保证金、今昨仓或期货公司联调 |
| `ctp_sim` | 本地具体合约、乘数、保证金、开平仓、今昨仓、异步回报和恢复语义演练 | 真实 CTP 连接或期货公司模拟前置通过 |
| `ctp` | 仅本地 fake front 可测的协议骨架 | 真实连接、认证、结算确认或任何真实账户操作 |

仓库有一个 `simulated` 画像用于本地 `ctp_sim` 演练；没有 production 画像。`CtpBrokerAdapter`
目前仅接受内存 fake front 做协议测试，应用 composition root 仍会在尝试连接前拒绝 `ctp`；没有真实
CTP 的认证、结算确认、报单、撤单、回报订阅或查询适配器。

## 已有执行基础设施

- 目标在收盘后冻结为带批次身份的日频快照；执行读取冻结目标，而不是重新计算信号；
- 订单使用幂等身份、持久化 attempt、账户级执行租约和终态恢复；
- 日线期货计划器可将连续研究目标映射到具体合约，并按乘数、权益和动态保证金换算整数
  手数；反手会拆分平昨、平今和开仓语义；
- `paper` 与 `ctp_sim` 支持订单/成交状态、撤单、重启恢复和对账演练；
- preflight、盘中风险结论、交易前检查和 kill switch 是彼此独立的最后防线。

## 账本与结算事实

订单、成交、撤单、账户与持仓快照均以追加式记录保存；持仓快照同时保留保证金以及已实现/未实现
PnL。每日结算以独立的券商结算身份、结算日、账户快照关联、现金、保证金、费用和证据追加，不能
覆盖旧快照或被同一身份的不同内容重写。

更正必须作为独立的 controlled adjustment 追加，且必须具备唯一调整身份、具名审批人、原因、金额、
发生时间和可审计证据。调整不会修改订单、成交、结算或账户历史，也不能通过重启、环境变量或自动
任务写入。真实 CTP 结算单导入仍待真实适配器与人工授权，当前仅支持本地 `paper` / `ctp_sim` 的
持久化演练。

## 执行故障矩阵

下列路径均在本地 PostgreSQL、`paper`、`ctp_sim` 或 fake front 下验证；任一未知或冲突状态都不允许
创建新风险。

| 故障 | 失败关闭行为 | 覆盖测试 |
| --- | --- | --- |
| disconnect / restart | 断连拒绝操作；重连后只同步并对账持久化状态 | `test_ctp_sim_broker.py`、`test_ctp_sim_recovery.py` |
| duplicate fill / unknown order | 成交以 execution identity 幂等；未知券商订单触发对账 HALT | `test_trade_attribution_repository.py`、`test_reconciliation_state.py` |
| stale price | 超过报价新鲜度阈值时 runtime risk 阻断提交 | `test_runtime_risk.py` |
| DB unavailable | 订单意图无法持久化时不会调用 broker | `test_durable_order_submission.py` |
| timeout / network partition | 提交进入 `SubmissionUnknown`，只能对账恢复，不得重发 | `test_durable_order_submission.py`、`test_durable_order_recovery.py` |
| position mismatch | 事务性回滚状态写入并留下失败审计 / HALT | `test_reconciliation_state.py` |
| insufficient margin | `ctp_sim` 拒绝开仓，且不创建委托 | `test_ctp_sim_broker.py` |
| price limit | 可信涨跌停边界触发 pre-trade 拒绝 | `test_execution_failure_matrix.py` |
| cancel reject | 保存 `CancelRequestFailed`，绝不宣称已撤单 | `test_durable_order_cancellation.py` |
| session rollover | 今仓显式结转昨仓；平仓必须使用正确的今昨仓语义 | `test_ctp_sim_broker.py` |

`test_trading_execution_e2e.py` 现覆盖完整的受门禁本地链路：`P2 candidate → named activation →
PortfolioTarget → ApprovedPortfolioTarget → P8 provenance replay → one-time durable consumption → ctp_sim →
Fill → Position → Reconciliation`。该测试只使用模拟账户和隔离 PostgreSQL，不能被理解为真实 CTP 或
实盘验收，也不允许调用方手写 `StrategyTarget`、风险 hash、`ExecutionPlan`、`PreflightResult` 或订单。
P8-WP04 的
`application.execution_provenance_preflight.ExecutionProvenancePreflight`：它必须重放每一条原始
Research activation request 并精确比对 claimed receipt，拒绝只给 `StrategyTargetActivationRef`、手写
activation hash 或 synthetic target 的来源；随后重放 P3 portfolio/risk approval，绑定 PIT manifest、账户/
持仓、`ctp_sim_market_data` 报价和具有有效窗口的具体合约/保证金规则，并在内部生成 P5 plan、runtime-risk
assessment 与 `PreflightResult`。调用方不能传入手写 `ExecutionPlan` 或 `PreflightResult`。

WP04 回执只是一份短时 hash-bound 的 `ctp_sim` **证据**，三个 eligibility 字段均永久为 `false`，没有
broker、router、submit/cancel、recovery 或数据库能力。它也不把静态 P2 的 `decision_time_safe=false` 升级为
交易授权。P8-WP05 的 `CtpSimCandidateExecutor` 才会以原始 request 为输入，在最终边界重新获取并验证
simulator account/state/quotes、rule、runtime-risk 和 P5 preflight，然后从内部 plan 派生 exact canonical order。
它把 `(broker, account, plan_hash, order_hash)` append-only consumption 与 durable order intent 同事务提交；
只有 executor 可签发的不透明 `CtpSimSubmissionAuthority` 才能同时绑定 durable 和 simulator，任意
duck-typed/no-op guard 都不能绕过。`CtpSimBrokerAdapter` 在自身状态锁内把 exact consumption 与真实
state/quote 基线传给 `assert_reserved`，而每个成功的 batch leg 才能更新此基线；状态变化、报价变化或崩溃后的
未知结果都会失败关闭。legacy `live execute` 对 `ctp_sim` 提交明确拒绝；candidate reconciliation 不接受
调用方 snapshot，强制读取 simulator，并要求每个 simulator order/fill 都有 consumption，否则写入粘性 `HALT`。
该真实 candidate E2E（含双合约 batch）已使
`Portfolio/Risk→CTP sim` candidate seam 为 `VERIFIED`，但 candidate matrix、WP04 receipt 与所有 live
eligibility 仍不产生交易授权。

## 对账差异与人工恢复

对账将券商订单、成交、持仓和账户快照与内部订单/账本逐项关联。缺少稳定订单身份、账户不一致、
无法关联到内部订单的券商订单或成交、以及任何身份或数量冲突，都会回滚该次状态写入，并为该
`profile + broker + account` 追加带哈希链的 `HALT` 审计记录。

`HALT` 是粘性的：后续成功对账或新的 runtime-risk PASS 都不能自动解除它；每笔非 `paper` 提交会读取
此状态并拒绝 `HALT` / `MANUAL_RECOVERY`。恢复只能依次由同一具名负责人执行
`HALT → MANUAL_RECOVERY → NORMAL`，每一步都要写入理由和审计证据。仓库不会自动恢复交易或替人工
确认差异已经解释。
- 日历事实采用离线、版本化、按稳定品种枚举的 Calendar Snapshot；Application 只在最终实际
  合约身份已由券商适配器补全后复核明确会话，并要求同一时点也在实际月份 Contract Rule Snapshot
  的同名会话内；未知、假日、盘外、来源未验证、PIT 不可见或规则会话不匹配一律阻断。

连续合约永远不能直接下单。真实 CTP 映射必须显式维护
`continuous_symbol → data_symbol → instrument_id + exchange_id`，并附带品种、乘数、
最小变动价位和人工启用状态。当前 `configs/instruments/ctp.yaml` 默认空映射，任何缺失或
未启用映射都会失败关闭。

## 当前不能做什么

以下命令接口存在，不等于当前可以对真实账户执行：

- `uv run --offline --no-sync northstar live signal`、`risk-check`、`execute`、`sync`、`poll`、`cancel-stale`
  都会经过画像、broker、数据、preflight 和风险门禁；
- 当前没有 production 画像，因此 `uv run --offline --no-sync northstar live scheduler` 会失败关闭；
- `NORTHSTAR_BROKER=ctp` 会在尝试连接前拒绝；
- `NORTHSTAR_LIMIT_CHASE_*` 是未来多轮追价设计参数，当前主流程不会把它们解释为已启用的
  真实追价策略；
- 交易日历核心已经具备，但尚无经授权、可验证的 runtime Calendar Artifact；因此
  `futures.calendar_artifact_snapshot_hashes` 为空、使用 test fixture，或制品的内容、血缘、来源授权
  不可验证时，仍会阻断执行。
  不能以 `XSHG`、工作日推断或公开参考规则替代实际期货夜盘会话；期货公司费率和账户级动态规则
  同样尚未达到 production 数据门槛。

Dashboard 只用于本地查看数据、报告、订单和运行健康摘要；不要将其暴露到公网，也不要把
可视化结果当作交易许可。

## 真实 CTP 前不可跳过的条件

在创建 production 画像或实现真实 broker adapter 前，至少需要：

1. 经书面授权的市场数据、权威交易日历/会话、实际合约链和动态规则快照；
2. `CTPBrokerAdapter` 的认证、结算确认、报单、撤单、查询、回报订阅、重连与身份映射；
3. 期货公司模拟前置上的断网、重启、重复/迟到回报、部分成交、撤单失败和日终对账演练；
4. 账户级风险状态、kill switch、人工审批、恢复 runbook 和审计记录；
5. 研究准入、simulated 阶段和 production 阶段的独立人工批准。

这些条件不能由 `paper` 或一次成功的 `ctp_sim` 演练替代。供应商和研究准入边界见
[研究准入政策与数据治理](09_研究准入政策与数据治理.md)。
