# 实盘执行现状与边界

## 当前具备的能力

Northstar Quant 已具备单轮 paper / live 编排：

1. 读取 production profile 与市场数据
2. 运行 canonical strategy pipeline
3. 同步券商账户、持仓、全客户端 API 挂单和近期成交
4. 执行 live preflight
5. 生成并持久化 execution plan
6. 执行交易前风险检查
7. 在每次提交前重读 kill switch 与授权配置
8. 通过 Paper 或 IBKR adapter 提交
9. 对账、记录运行健康并发送告警

可安全用于诊断的入口：

```bash
uv run northstar live preflight --profile cn_etf_daily
uv run northstar live preview-rebalance --profile cn_etf_daily
```

`live run`、scheduler、撤单、轮询和同步在非 paper 模式下都属于外部交易状态操作，必须明确确认账户和运行目标。

## 本轮已收紧的安全行为

- IBKR 默认只读，追价最终默认撤单。
- `demo`、缺少 manifest 或未显式 eligible 的数据不能进入真实下单。
- 真实账户缺少权益、可用资金、账户归因或账户身份时 fail-closed。
- 订单 side / type / qty / price / notional 使用严格校验。
- 追价前一订单未确认撤销时，不会提交下一订单。
- 部分成交后只处理确认未成交的剩余数量。
- `UnknownTerminal` 会停止整个订单批次并等待对账。
- 每次提交前重新读取 kill switch、live enabled、readonly、account 和交易日历。
- IBKR 不再伪造缺失的 broker order ID。
- IBKR 订单设置由 `plan_id + attempt_no` 派生的稳定 `orderRef`。
- IBKR 状态按显式目标账户过滤，成交方向统一为 `BUY / SELL`。
- 每个实际提交 attempt 都先持久化为 `Prepared`，原子切换到
  `Submitting` 后才允许触达券商。
- 订单使用 `broker + account + idempotency_key`、`orderRef`、`permId` 和
  `clientId + orderId` 的分层唯一约束；同一幂等键出现不同载荷立即阻断。
- 实盘执行按 `broker + account` 获取数据库租约，租约接管会递增 fencing
  token；旧 owner 不能续约、释放或认领新订单。
- 执行批次和 plan identity 按策略输出时间稳定派生，不再依赖随机进程身份。
- instrument registry 同时覆盖下单、行情、持仓、订单和成交的 conId 映射。
- IBKR 对账主动读取 API completed orders，按 `orderRef` 恢复崩溃窗口中的
  本地订单，并把 `PendingCancel` 推进到券商确认终态。
- `ib_async` completed 回调缺少原始 orderId/clientId 时，使用
  `orderRef + permId + conId` 恢复，并从 `Order.filledQuantity` 读取进度。
- 成交按 `broker + account + execId` 持久化去重，并按
  `orderRef/permId/clientId/orderId/conId` 完整身份匹配和回填本地订单。
- 超时撤单只查询精确 broker/account/client/order 身份；先写
  `CancelPrepared`，券商接受请求后再推进为 `PendingCancel`。
- `CancelRequestFailed` 仍会阻断新提交，直至 completed order 强身份恢复；
  已终态订单不会再创建重复撤单意图。
- 追价策略把 max-steps、fallback 和限价偏移持久化为 policy fingerprint；
  重启会校验全部 attempt，配置扩张、收缩或语义漂移都不会新增或遗漏订单。
- 运行健康记录先持久化，告警失败不覆盖已有交易结果。

## 已落地的崩溃恢复协议

### 1. 提交幂等状态机

每个追价 attempt 都执行：

```text
Prepared（已提交数据库）
  → Submitting（持有效租约和 fencing token 的 CAS）
  → Submitted / Filled / Rejected / 其他券商确认状态
  → SubmissionUnknown（调用可能已经生效但没有确认回执）
```

`Submitting` 和 `SubmissionUnknown` 不会自动重发。下一次运行先读取 open /
completed orders 和 executions；能够用 `orderRef` 证明身份时更新原记录，仍
无法证明时继续阻断账户执行。

### 2. 跨进程租约

CLI 与 scheduler 共用 `run_live_once` 的账户级租约。租约在读取账户快照前
获取，避免等待进程使用过期快照；提交、状态轮询和追价撤单期间持续 heartbeat。
过期接管递增 fencing token，旧进程的数据库 CAS 会失败。

### 3. Instrument 映射内容

系统已经提供受配置管理的 IBKR instrument registry：

```text
data_symbol ↔ broker_symbol ↔ conId ↔ secType ↔ exchange ↔ primaryExchange ↔ currency
```

adapter 不再根据 symbol 动态猜测合约。下单前会要求映射存在且启用，先把
完整身份写入持久化订单载荷，再构造 Contract，并要求 IBKR qualification
返回的 `conId` 与配置精确一致。行情、持仓、订单和成交也通过 `conId`
反解回数据 symbol。

仓库默认 registry 为空，未录入任何未经核验的真实 `conId`；因此当前仍会阻断
所有 IBKR 下单。实盘解锁前必须由账户持有人逐项在 TWS / IB Gateway 核验并
审计配置内容。

### 4. 订单终态与历史兼容

订单 attempt 会保存 `orderRef/clientId/permId/conId`、成交数量和均价。
对账合并 open 与 completed orders；只有券商返回明确终态时才会更新
`PendingCancel`。撤单调用前先保存 `CancelPrepared`，避免崩溃窗口丢失撤单
意图。迁移前 broker 为空的历史订单仍会安全跳过自动撤单，需要人工核对后再
补录。

## 仍然阻断真实资金的事项

- 默认 instrument registry 为空，必须由账户持有人逐项核验实际 conId。
- 当前 production profile 和 manifest 使用 demo 数据且
  `live_trading_eligible: false`。
- SQLite 可用于本机验证，但正式多进程运行仍建议 PostgreSQL，并需要完成
  PostgreSQL 并发、进程强杀、断网和恢复演练。
- `SubmissionUnknown` 查不到券商证据时保持人工恢复，不提供猜测性自动重提。

## 回测命名说明

当前目标权重和策略仿真主要由项目内置引擎完成。`BacktraderBarSimulationBacktester` 兼容入口目前没有真正运行 Backtrader，`vectorbt` 也不是 canonical research pipeline 的实际实现。

在完成独立第三方引擎交叉验证前，不应把这些入口描述成已经建立了独立的“可信回测层”。

## 当前结论

当前版本适合研究、回测、架构验证和 paper soak，不应开启真实资金。实盘解锁条件与分阶段方案见 [架构审核与演进路线](10_架构审核与演进路线.md)。
