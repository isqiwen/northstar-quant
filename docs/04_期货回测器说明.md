# 期货回测器说明

项目只有一个回测命令入口。低频策略的常规流程由两种日线实现组成，分钟回放是可选的
上线前专项能力：

| 顺序 | 画像 / 引擎 | 定位 | 不解决的问题 |
|---|---|---|---|
| 日常 1 | `cn_futures_daily_trend_offline` / `weight_return` | 连续合约策略方向、参数和组合快速研究 | 保证金、换月、真实成交 |
| 日常 2 | `cn_futures_daily_actual_offline` / `futures_daily` | 实际合约逐日可交易性与保证金账户验证 | 日内事件顺序、排队和撤单时点 |
| 可选 | `cn_futures_intraday_replay_offline` / `futures_intraday_replay` | 容量、委托生命周期和部分成交专项回放 | 交易所 tick/L2 精确队列 |

三个画像均为 `offline/research`，且 `execution_allowed: false`。回测通过不代表可以连接
CTP 或提交真实订单。

## 统一审计合同与不可比边界

每次正式回测由唯一编排入口生成 `BacktestRequest`、`BacktestResult` 和 `RunManifest` v4。它会冻结
画像、策略目标、数据/PIT 证据、频率链、成本假设和代码工作树摘要；正式报告只能由已验证的
`BacktestRun` 生成。正式制品不记录墙钟生成时间；复用前会由同一冻结运行重新构建完整
`report.json` 和 `report.md` 并逐字节核对，不能信任报告文件自身声明的 checksum。不能把手工
JSON、另一份指标、缓存持仓，或联动改写的 Markdown/JSON/hash 拼到有效 manifest 上。

这三个引擎共享的是审计 envelope，**不是**同一种成交真实性：

- `weight_return` 不产生订单或成交事件；它只能给出连续研究序列的收益近似。
- `futures_daily` 记录目标约束和模拟成交事件，不包含订单生命周期。
- `futures_intraday_replay` 才记录分钟级订单、部分成交、撤单与拒绝事件，但仍不是交易所逐笔/L2 重建。

因此不得跨引擎比较订单数、成交数、成交成本或将模拟 fill 说成已闭合真实交易。正式清单的
`engine.fidelity`、`result.execution_audit` 和 `limitations` 是解释结果的唯一依据。

实际合约回测完成后，可运行同一工作流的候选研究准入评估：

```bash
uv run --offline --no-sync northstar research assess portfolio \
  --profile cn_futures_daily_actual_offline
```

当前公开工程样本会如实得到 `INSUFFICIENT_EVIDENCE`；这不会阻止报告生成，但不能提升为
simulated 或 production。授权、样本外和压力门槛由
[研究准入政策与数据治理](09_研究准入政策与数据治理.md)维护。

## 运行方式

```bash
uv run --offline --no-sync northstar backtest run portfolio \
  --profile cn_futures_daily_trend_offline

uv run --offline --no-sync northstar data download \
  --profile cn_futures_daily_actual_offline
uv run --offline --no-sync northstar backtest run portfolio \
  --profile cn_futures_daily_actual_offline

uv run --offline --no-sync northstar data import-file /path/to/actual_intraday.parquet \
  --profile cn_futures_intraday_replay_offline
uv run --offline --no-sync northstar backtest run portfolio \
  --profile cn_futures_intraday_replay_offline
```

实际合约日线画像使用 `akshare_actual_daily`：交易所实际合约日线来自 AKShare，
保证金、手续费、涨跌停和参考主力来自 AKShare 暴露的金十接口。主力和规则统一延迟到
下一交易日生效。规则快照与行情按日缓存；缺日、解析失败或主力不在前后两日合约链时
拒绝发布。公开规则不是期货公司账户费率，`research_position_limit_lots` 也是研究硬
上限而非交易所限仓，因此该数据仍是离线研究级。

## 日线实际合约契约

主键为 `date + symbol`，`symbol` 必须是 `RB2405` 之类的实际合约。

| 字段组 | 必需字段 |
|---|---|
| 身份 | `date`, `symbol`, `product`, `exchange` |
| 行情 | `open`, `high`, `low`, `close`, `settlement`, `pre_settlement` |
| 流动性 | `volume`, `open_interest` |
| 动态规则 | `upper_limit`, `lower_limit`, `margin_rate`, `max_position_lots` |
| 开仓费 | `commission_open_per_lot`, `commission_open_rate` |
| 平昨费 | `commission_close_per_lot`, `commission_close_rate` |
| 平今费 | `commission_close_today_per_lot`, `commission_close_today_rate` |
| 换月 | `active_contract`, `selection_date` |
| 时段 | `first_session`, `session_complete` |

每个 `date/product` 只能有一个主力合约，主力必须在当日合约链中，且
`selection_date < date`。逐日引擎依次执行换月、目标调仓、保护价、结算盯市和保证金
检查。成交应用 tick 滑点、动态费率、涨跌停、限仓和成交量参与率。

## 分钟实际合约契约

主键为 `timestamp + symbol`。除日线动态规则外，每行还必须包含：

| 字段组 | 必需字段 | 约束 |
|---|---|---|
| 交易日 | `date`, `timestamp`, `session` | `date` 是交易日归属；`session` 为 `night/day` |
| 分钟行情 | `open`, `high`, `low`, `close`, `volume`, `open_interest` | OHLC 位于当日涨跌停内 |
| 一档盘口 | `bid_price`, `ask_price`, `bid_volume`, `ask_volume` | `bid_price <= ask_price`，量可为 0 |
| 日终 | `settlement`, `pre_settlement`, `is_trading_day_end` | 每日每合约恰有一根日终 bar |
| 完整性 | `session_complete` | 缺夜盘或日盘时必须为 false，校验会拒绝 |

同一交易日/合约的动态规则必须保持一致。`timestamp` 严格递增，日终标记必须位于该
交易日/合约最后一根 bar。手续费率使用小数，例如万分之 0.5 写为 `0.00005`。

## 信号与成交

两个实际合约引擎都先将实际主力合约的单日收益链接成连续信号：

```text
index[t] = index[t-1] * close(active[t], t) / close(active[t], t-1)
```

换月日使用新合约自己的上一交易日收盘价作分母，因此跨合约价差不会污染趋势信号。
分钟画像原始频率是 `1m`，但 `data.signal_frequency: 1d`；策略决策和撮合数据不会混用。

分钟回放的固定规则：

1. 外部历史委托只能从 `submitted_at` 后的下一根该合约 bar 成交。
2. 市价单和可成交限价单读取买一/卖一、盘口量、tick 滑点和成交量参与率。
3. 被动限价单必须被分钟高低价触及，并先扣除 `queue_ahead_ratio` 排队量。
4. 未完全成交单保留部分成交状态，超过 `order_ttl_bars` 后过期；撤单在同 timestamp
   撮合前生效。
5. 反手和换月先平后开，开仓委托依赖平仓委托完全成交。
6. 每次开仓部分成交前重新检查动态限仓、账户权益、占用保证金和手续费。
7. 日终按结算价盯市；保证金不足时尝试按盘口强平，不能可靠完成时停止回放。

报告目录的 `report.json` 保存引擎标准化后的 `analytics`，`manifest.json` 保存 `RunManifest` v4。
分钟回放会提供委托生命周期、
部分成交、撤单和拒绝原因；日线实际合约引擎提供目标事件、资金/保证金和拒绝目标等
日频审计信息，但不应把它误称为逐笔订单回放。读取报告时必须先确认 `backtester` 与
`execution.detail_level`，不能跨引擎直接比较“交易数”或“拒单数”。

## 可信边界

连续合约用于快速淘汰策略，实际合约日线用于低频策略的主要可交易性验证。分钟回放只在
容量、部分成交或委托生命周期会影响结论时使用，不是常规回测门槛。日线与分钟回测都
不是实盘收益承诺；真实队列位置、隐藏流动性和网络延迟仍须用仿真柜台、CTP 演练及必要
时的 tick/L2 样本继续验证。

当前 legacy 市场投影与 immutable static as-of 快照都不会被本回测合同升级为候选策略。`RunManifest`
固定 `candidate_admission_eligible: false`，并把上游规则的观察状态写为
`research_admission.observed_policy_status`；即使观察状态为 `PASS`，仍必须经过逐决策 look-ahead
guard、验证框架和人工 Research Decision，才可能进入后续阶段。
